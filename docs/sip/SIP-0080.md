# SIP-0080 — Notifiche affidabili (SSE first, Telegram best-effort)

| Campo    | Valore |
|----------|--------|
| ID       | SIP-0080 |
| Stato    | Draft |
| Priorità | High |
| Dipende  | SIP-0062 (stream), SIP-0069 (i18n) |

## Problema

Nel flusso amichevoli/offerte/azioni manageriali alcuni eventi arrivano in `news_item` ma non arrivano su Telegram, quindi l'utente percepisce "notifiche perse".

## Obiettivo

1. Canale principale in-app sempre affidabile (header badge + pagina news + SSE).
2. Telegram non blocca mai il flusso: invio asincrono e best-effort.
3. Tracciabilità di consegna (inviato/fallito/tentativi) per debug.

## Architettura proposta

1. **Fonte unica evento**
   - Tutti gli eventi scrivono prima su `news_item`.
   - `news_item` è la sorgente verità per UI e storico.

2. **Distribuzione realtime**
   - SSE (`/notification/stream`) pubblica eventi appena creati.
   - Fallback polling resta attivo (graceful degradation).

3. **Telegram async**
   - Al posto del send inline nei controller, creare job `notification_dispatch`.
   - Worker processa coda con retry (`max_attempts`, backoff progressivo).
   - Se Telegram fallisce: evento resta comunque visibile in-app.

4. **Tabella delivery (osservabilità)**
   - Nuova tabella `notification_delivery`:
     - `id`, `news_item_id`, `channel` (`telegram|push|email`), `status`,
       `attempts`, `last_error`, `sent_at`, `created_at`, `updated_at`.
   - Permette dashboard admin e troubleshooting veloce.

5. **Canali futuri**
   - Web Push opzionale come secondo canale istantaneo quando Telegram non disponibile.

## Implementazione step-by-step

1. Estrarre servizio unico `NotificationDispatcher::enqueue($newsItemId, $channels)`.
2. Sostituire invii diretti Telegram nei controller con enqueue.
3. Aggiungere worker `yii notification/dispatch` (cron ogni minuto o daemon).
4. Aggiungere `notification_delivery` + indici (`news_item_id`, `channel`, `status`).
5. Aggiornare friendly/transfer/staff flow per usare sempre pipeline unica.

## Criteri di accettazione

1. Se Telegram è offline, news badge/SSE continuano a funzionare senza perdita evento.
2. Ogni evento crea almeno una riga `notification_delivery`.
3. Retry automatico visibile in DB (`attempts` incrementa, `last_error` valorizzato).
4. Nessun controller fallisce per errore canale esterno.

## Note operative

- Short term: mantenere invio Telegram inline dove già patchato, ma instradare gradualmente al dispatcher.
- Long term: i controller non dovranno conoscere Telegram direttamente.
