# SIP-0077 — Go Orchestrator Hard-Cut (No Cron, Reset DB)

| Campo    | Valore |
|----------|--------|
| ID       | SIP-0077 |
| Titolo   | Motore continuo Go per scheduler + trigger |
| Stato    | Proposed |
| Autore   | Gold Manager Dev Team |
| Data     | 2026-05-28 |
| Priorita | Alta |

---

## Obiettivo

Sostituire cron PHP con un unico **orchestratore Go** che:

1. esegue job a orari pianificati
2. esegue job immediati su trigger evento
3. centralizza lock, retry, idempotenza, audit

Vincolo progetto: ambiente alfa/beta, downtime accettato, reset DB accettato.

---

## Decisione

Approccio **hard-cut**:

- cron disabilitati
- nuova pipeline orchestration in Go
- schema DB nuovo per scheduling/eventi
- reset dati legacy ammesso
- world reseed da zero

Nessuna compatibilita retro obbligatoria.

---

## Scope

### In scope

- scheduler continuo Go (polling + timer wheel)
- trigger eventi dominio (market bid, friendly start-now, admin trigger, ecc.)
- worker executor con lock distribuito
- tabelle nuove orchestrazione
- outbox per SSE/news/telegram
- script reset+bootstrap

### Out of scope (fase iniziale)

- multi-instance leader election avanzata (si puo partire single instance)
- cross-region orchestration
- storico compatibile con vecchio modello cron

## Architettura proposta

## 1) Componenti Go

- `scheduler`: calcola prossime run (`cron expr` o schedule spec)
- `dispatcher`: crea job eseguibili e li mette in coda
- `executor`: esegue handler dominio con lock/idempotenza
- `event-consumer`: consuma trigger da DB queue/outbox
- `notifier`: pubblica SSE/news/telegram post-commit

---

## 2) Tabelle nuove

### `orchestrator_schedule`

- `id`
- `job_name` (unique)
- `enabled`
- `cron_expr` (o schedule json)
- `timezone`
- `next_run_at`
- `payload_json`
- `updated_at`

### `orchestrator_event`

- `id`
- `event_type`
- `aggregate_type`
- `aggregate_id`
- `payload_json`
- `status` (`pending|processing|done|failed`)
- `attempts`
- `available_at`
- `created_at`
- `processed_at`

### `orchestrator_run`

- `id`
- `source_type` (`schedule|event`)
- `source_id`
- `job_name`
- `idempotency_key` (unique)
- `status` (`running|ok|failed|skipped`)
- `started_at`
- `finished_at`
- `error_text`
- `metrics_json`

### `orchestrator_outbox`

- `id`
- `channel` (`sse|news|telegram`)
- `topic`
- `payload_json`
- `status` (`pending|sent|failed`)
- `attempts`
- `created_at`
- `sent_at`

---

## 3) Trigger model

Ogni azione sincrona API che richiede effetto immediato:

- salva stato dominio (transazione)
- scrive `orchestrator_event` nella stessa transazione
- ritorna subito a client
- orchestratore consuma evento quasi real-time

Esempi:

- nuova offerta asta -> `market.bid.placed`
- click “inizia ora” -> `friendly.start_now`
- admin advance-day -> `time.advance`

---

## 4) Idempotenza e lock

- ogni run genera `idempotency_key` deterministico
- unique key evita doppia esecuzione
- lock distribuito (Redis) su job critici:
  - `lock:market:resolve`
  - `lock:fixture:run`
  - `lock:economy:daily`

Se lock non disponibile: run = `skipped` e retry pianificato breve.

---

## 5) Config ENV nuova

- `GM_ORCHESTRATOR_ENABLED=1`
- `GM_ORCHESTRATOR_POLL_MS=1000`
- `GM_ORCHESTRATOR_WORKERS=8`
- `GM_ORCHESTRATOR_TZ=Europe/Rome`
- `GM_ORCHESTRATOR_LOCK_TTL_SEC=60`
- `GM_ORCHESTRATOR_RETRY_MAX=8`
- `GM_ORCHESTRATOR_RETRY_BACKOFF_MS=1500`
- `GM_CRON_ENABLED=0` (hard-cut)

3. **Handlers dominio**

## Script operativi richiesti

### `scripts/reset-and-bootstrap.sh`

Fa:

1. stop app writers
2. drop/recreate DB
3. migrate fresh
4. seed world base (IT/EN)
5. start orchestrator
6. smoke test comandi base

### `scripts/smoke-orchestrator.sh`

Verifica:

- schedule run scatta
- trigger event consumato
- run registrata in `orchestrator_run`
- outbox consegna almeno 1 messaggio

---

## Acceptance criteria

- nessun cron necessario per gameplay core
- job pianificati eseguiti dal solo orchestratore
- trigger utente eseguiti in near real-time
- doppie esecuzioni prevenute da idempotenza
- reset + bootstrap completabile da script unico
- sistema riavviabile da zero senza interventi manuali

---

## Rischi e mitigazioni

1. **Race conditions job concorrenti**
   - lock redis + idempotency unique

2. **Bug in porting logica cron**
   - smoke e2e su ogni flusso prima cut finale

3. **Perdita notifiche**
   - outbox persistente + retry

4. **Single point failure orchestratore**
   - restart policy container + healthcheck

---

## Note finali

Questa SIP assume esplicitamente:

- ambiente non production-critical
- possibile perdita dati storici accettata
- priorita: velocita evoluzione architettura + coerenza runtime

Con questo modello, gameplay diventa event-driven e molto piu prevedibile.
