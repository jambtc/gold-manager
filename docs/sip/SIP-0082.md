## 1. Motivazione

Gold Manager v2 opera con una valuta interna (€) gestita interamente lato DB.
Questo modello ha tre limiti strutturali:

1. **Nessuna verificabilità** — le transazioni (salari, trasferimenti, sponsor) sono
   opache: solo il server conosce i movimenti.
2. **Nessuna interoperabilità** — la moneta di gioco non può uscire dal silo,
   impedendo future integrazioni (marketplace cross-game, NFT giocatori, tornei
   multi-piattaforma).
3. **Scalabilità multi-nazione rischiosa** — con 20 paesi e migliaia di team,
   un bug nell'`EconomyController` PHP può corrompere l'intera base monetaria
   senza audit trail indipendente.

La proposta è di introdurre **Gold Manager Coin (GMC)**, un token ERC-20 su
**Hyperledger Besu** (rete privata/consorzio), che diventa la rappresentazione
on-chain della valuta di gioco. Il DB PHP rimane la fonte di verità per la
logica di gioco; la blockchain è la fonte di verità per i saldi.

---

## 2. Perché Hyperledger Besu

| Criterio | Besu (privato) | Ethereum mainnet | Polygon PoS |
|----------|---------------|-----------------|-------------|
| Gas cost | Zero (privata) | €0.10–10/tx | €0.001/tx |
| Throughput | 1,000+ TPS | ~15 TPS | ~7,000 TPS |
| Privacy | Totale (nodi controllati) | Pubblica | Pubblica |
| Compatibilità EVM | 100% | — | 100% |
| Finality | Istantanea (IBFT2) | ~12 sec | ~2 sec |
| Permissioning | Nativo | No | No |
| Dipendenza esterna | Nessuna | Alta | Alta |

Besu con consenso **IBFT 2.0** (Istanbul BFT) garantisce finalità immediata
e nessun costo di gas — cruciale per micro-transazioni frequenti come i
pagamenti settimanali di stipendi.

## 6. Decisione architetturale critica: FIXED vs MINTABLE

Questa è la scelta più impattante del design. Non viene decisa in questo SIP
ma le implicazioni devono essere comprese prima dell'approvazione.

---

### 6.1 Opzione A — Fixed Supply (10B al genesis, no mint)

```solidity
// Tutto il supply è creato in deploy, distribuito ai pool
constructor() ERC20("GoldManagerCoin", "GMC") {
    _mint(msg.sender, 10_000_000_000 * 10**decimals());
}
// Nessuna funzione mint() esiste
```

**Vantaggi:**
- Massima fiducia: nessuno può inflazionare la moneta dopo il deploy
- Semplicità del contratto (minor superficie di attacco)
- Prevedibilità per i manager: il valore del loro budget non si diluisce
- Standard de-facto per token "store of value"

**Svantaggi:**
- Se il gioco cresce oltre 20 paesi, i token si esauriscono
- I token "bruciati" (burn di player, trasferimenti internazionali) riducono
  permanentemente il supply → deflazione progressiva non controllabile
- Nessuna flessibilità per eventi speciali (coppe mondiali, espansioni massive)
- Richiede una previsione accurata del crescita sin dal day-1

**Quando scegliere:**
→ Se il gioco è concepito come prodotto finito con N paesi massimi noti,
  o se si vuole comunicare scarsità come valore di marketing.

---

### 6.2 Opzione B — Mintable con governance (supply espandibile)

```solidity
// Solo il ruolo MINTER può creare nuovi token
bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");

function mint(address to, uint256 amount) external onlyRole(MINTER_ROLE) {
    require(totalSupply() + amount <= MAX_SUPPLY, "cap exceeded");
    _mint(to, amount);
}

uint256 public constant MAX_SUPPLY = 50_000_000_000 * 10**decimals(); // hard cap 50B
```

**Vantaggi:**
- Flessibilità per l'espansione: ogni nuovo paese sblocca quote proporzionali
- Permette di rispondere a shock economici (crollo del prezzo, stagflazione interna)
- Hard cap a 50B garantisce comunque un tetto superiore noto
- Modello usato da quasi tutti i token di gaming (Axie Infinity AXS, Gala, ecc.)

**Svantaggi:**
- Richiede governance robusta per il `MINTER_ROLE`
  (chi ha la chiave? multisig? DAO? il server PHP?)
- Rischio di inflazione se il minting è troppo aggressivo
- Complessità contrattuale maggiore (AccessControl, TimeLock, Governance)
- Manager potrebbero percepire il mint come "svalutazione"

**Quando scegliere:**
→ Se si prevede crescita organica non lineare, o se il gioco è
  concepito come ecosistema aperto con meccanismi DeFi futuri.

---

### 6.3 Opzione C — Ibrida: Fixed con Burn-and-Reissue

```
Supply iniziale: 10B GMC (fisso, no mint)
Meccanismo: burn esplicito → treasury sblocca quota equivalente
Risultato: il supply circolante fluttua, il supply totale è fisso
```

**Logica:**
```
Burn event (es. player retirement, stadium demolition)
    → GMC vengono distrutti dalla circolazione
    → treasury è autorizzata a re-emettere fino al burned amount
    → netto: supply totale non cambia mai
```

**Vantaggi:**
- Combina la prevedibilità del fixed con la flessibilità della governance
- Burns incentivano attività di gioco (il "bruciare" un token ha significato)
- Audit trail completo on-chain

**Svantaggi:**
- Logica contrattuale più complessa
- Il treasury deve tenere traccia delle quote burn/reissue
- Meno standard, richiede documentazione dettagliata per i manager

## 7. Flusso on-chain delle transazioni di gioco

```
┌──────────────────────────────────────────────────────────┐
│                   GAME SERVER (PHP)                      │
│  EconomyController::actionPayWages()                     │
│    ↓                                                     │
│  GMCBridge::transferBatch(recipients[], amounts[])       │
│    ↓ (firma con chiave privata del server)               │
└────────────────────────┬─────────────────────────────────┘
                         │ JSON-RPC
                         ▼
┌──────────────────────────────────────────────────────────┐
│               HYPERLEDGER BESU NODE                      │
│  GoldManagerCoin.sol                                     │
│    GameEconomy.sol (contratto orchestratore)             │
│    ├── payWages(teamId, playerAddresses[], amounts[])    │
│    ├── transferFee(sellerId, buyerId, fee, salary)       │
│    ├── creditMatchRevenue(teamId, amount)                │
│    ├── creditSponsor(teamId, amount)                     │
│    └── upgradeStadium(teamId, cost)                      │
└──────────────────────────────────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────────┐
│              WALLET MANAGER (per ogni utente)            │
│  Indirizzo Besu derivato da userId                       │
│  Saldo GMC visibile su /wallet endpoint                  │
│  Esportabile su MetaMask (Besu RPC)                      │
└──────────────────────────────────────────────────────────┘
```

### Dual-ledger durante la transizione

Durante la fase di integrazione, DB e blockchain coesistono:

```
Phase 1: PHP DB è source-of-truth, Besu è mirror (read-only audit)
Phase 2: Scritture critiche (stipendi, trasferimenti) su Besu prima del DB
Phase 3: DB diventa cache di Besu (replica on-demand)
```

## 8. Stima del volume transazionale

### Per paese per settimana (48 team)

| Evento | Frequenza | Tx/settimana |
|--------|-----------|-------------|
| Stipendi giocatori | 48 team × 23 player | 1,104 |
| Stipendi staff | 48 team × 5 staff | 240 |
| Sponsor installment | 48 team × 1 | 48 |
| Transfer bids/resolution | ~30 aste/settimana | 60–120 |
| Match revenue | 48 home match/week | 48 |
| Stadium upgrade | ~2/settimana | 2 |
| **Totale** | | **~1,600 tx/sett** |

Su base giornaliera: ~230 tx/giorno per paese.
Con 10 paesi: ~2,300 tx/giorno → **~0.027 tx/secondo** (Besu regge migliaia di TPS).

Batch processing (es. tutti gli stipendi in una tx multicall) riduce il numero
effettivo di tx di un fattore 10–20x → **volume abbondantemente gestibile**.

## 9. SIP complementari necessari

Questo SIP definisce l'economia e la filosofia. I seguenti SIP implementativi
sono necessari per completare l'integrazione:

### SIP-0083 — Smart Contract Suite

**Ambito:** progettazione e deployment dei contratti Solidity su Besu.

Contratti da sviluppare:
- `GoldManagerCoin.sol` — ERC-20 base (OpenZeppelin)
- `GameEconomy.sol` — orchestratore delle transazioni di gioco
- `TimeLock.sol` — delay obbligatorio su operazioni treasury
- `Governance.sol` (opzionale, solo per Mintable) — votazioni on-chain

**Sì, un contratto ad hoc è necessario** — non basta il semplice ERC-20.

Il contratto `GameEconomy.sol` deve:
```solidity
interface IGameEconomy {
    // Pagamento batch stipendi in una singola tx
    function payWagesBatch(
        address[] calldata recipients,
        uint256[] calldata amounts,
        uint256 teamId,
        uint256 weekNumber
    ) external;

    // Trasferimento giocatore: fee al venditore, salary da pool
    function executeTransfer(
        address seller,
        address buyer,
        uint256 transferFee,
        uint256 firstSalaryAdvance,
        uint256 playerId
    ) external;

    // Credito partita (biglietteria + sponsor)
    function creditMatchRevenue(address team, uint256 amount) external;

    // Upgrade stadio (debit dal wallet team)
    function upgradeStadium(address team, uint256 cost) external;

    // Emergency pause (multisig)
    function pause() external onlyRole(PAUSER_ROLE);
}
```

**Il contratto custom è la differenza tra un token e un sistema di pagamento
verificabile.** Senza `GameEconomy.sol`, si riduce a un DB on-chain senza
semantica di gioco.

### SIP-0084 — Wallet Manager UI

**Ambito:** interfaccia utente per visualizzare e gestire il wallet GMC.

- Dashboard saldo GMC
- Storico transazioni on-chain
- Export verso MetaMask (Besu custom network)
- QR code wallet address
- Blocco operazioni se saldo insufficiente

---

### SIP-0085 — PHP ↔ Besu Bridge

**Ambito:** layer di integrazione tra EconomyController PHP e i nodi Besu.

- `BesuClient.php` — wrapper JSON-RPC
- `GmcTransaction.php` — firma e broadcast transazioni
- Fallback graceful: se Besu non risponde, PHP continua su DB (Phase 1 dual-ledger)
- Queue per retry transazioni fallite
- Monitor: alert se Besu lag > 5 secondi

---

### SIP-0086 — Besu Node Infrastructure

**Ambito:** deployment e governance della rete privata.

- Topologia: 4 nodi validatori (IBFT 2.0), 2 nodi observer
- Docker compose + Helm chart per Kubernetes
- Permissioning list (solo nodi autorizzati)
- Backup chiavi (HSM o Vault)
- Monitoring: Prometheus + Grafana (block height, TPS, peer count)

## 12. Decisione aperta: Fixed vs Mintable

> **Questa decisione NON è presa in questo SIP.**
>
> Prima dell'approvazione è necessario rispondere a:
>
> 1. Qual è il numero massimo di paesi pianificato nei prossimi 3 anni?
> 2. Vogliamo che GMC abbia valore percepito esterno (scambio, listing)?
> 3. Chi detiene il `MINTER_ROLE` e con quale governance?
> 4. Accettiamo la complessità di TimeLock + Multisig per Mintable?
>
> **Raccomandazione tecnica:** iniziare con **Fixed Supply 10B GMC**
> con una `rescue clause` contrattuale: se il supply scende sotto
> il 10% del circolante necessario (verificato on-chain), una
> governance vote può approvare un singolo mint straordinario
> non superiore al 20% del supply corrente.
>
> Questo combina la semplicità del Fixed con una rete di sicurezza
> controllata, senza aprire la porta all'inflazione arbitraria.
