# SIP-0018: Multiplayer Synchronization

- Status: Accepted (Implemented Baseline)
- Type: Multiplayer
- Created: 2026-05-14

## Abstract

Define synchronization rules for multiplayer gameplay and concurrent command safety.

## Goals

- Consistent league state
- Reliable scheduling
- Conflict prevention
- Fair gameplay

## Requirements

The server SHALL remain authoritative.

Clients SHALL NOT directly modify game state.

## Implemented baseline (2026-05-27)

- Redis-first distributed lock service with cache fallback:
  - prevents parallel conflicting writes on transfer/friendly/live command endpoints.
- Idempotency guard (`X-Idempotency-Key` or deterministic request fingerprint):
  - duplicate POST retries are ignored safely.
- Transfer concurrency hardening:
  - offer accept path now uses lock + conditional status transitions + transaction wrapper.
- Friendly challenge concurrency hardening:
  - challenge/respond/start-now now protected against double submit races.
- Live command channel hardening:
  - substitution/tactic duplicate-click protection.
- Request traceability on critical write tables:
  - `transfer_offer`, `friendly_challenge`, `match_command` now include
    `request_id` and `request_source` fields (migration `m260527_210000_add_sync_audit_fields`).
