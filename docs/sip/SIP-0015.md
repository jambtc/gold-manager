# SIP-0015: API Versioning

- Status: Accepted (Implemented)
- Type: API
- Created: 2026-05-14
- Implemented: 2026-05-27

## Abstract

Define and apply API versioning strategy for public application endpoints.

## Specification

APIs SHALL use explicit versioning.

Example:

- /api/v1/
- /api/v2/

## Goals

- Backward compatibility
- Stable integrations
- Mobile support

## Deprecation policy

Deprecated APIs SHALL remain available during transition periods.

## Implementation in v2

Implemented baseline in `v2`:

- Canonical route: `GET /api/v1/user/status`
- Legacy alias retained: `GET /api/user/status`
- API schema route: `GET /swagger/openapi`
- API docs UI route: `GET /swagger`
- OpenAPI file generation route: `GET /swagger/generate`
- Legacy alias now returns deprecation headers:
  - `Deprecation: true`
  - `Sunset: Thu, 31 Dec 2026 23:59:59 GMT`
  - `Link: </api/v1/user/status>; rel="successor-version"`

This keeps old clients working while all new clients must target `/api/v1/*`.

## Swagger implementation notes

- Added dedicated Swagger views (`v2/views/swagger/*`) and dedicated layout (`v2/views/layouts/swagger_layout.php`).
- Added OpenAPI annotations (`@OA`) under `v2/controllers/api/v1/*` to support `\OpenApi\Generator::scan(...)`.
- `swagger/generate` writes `runtime/openapi/swagger.json` and shows result page.
