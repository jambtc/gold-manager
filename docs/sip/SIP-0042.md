# SIP-0042 — Event-Driven Live View: SSE-Only Architecture

| Field   | Value                 |
|---------|-----------------------|
| Status  | Accepted (Implemented) |
| Author  | Gold Manager Dev Team |
| Created | 2026-05-19            |

## Problem

### Current architecture (polling)

```
SimulateMatchJob (PHP, 2s/tick)
    │
    ▼ writes events to DB
MariaDB (match_event table)
    ▲
    │ GET /fixture/get-events?lastEventId=X  (every 2s)
Browser
    │
    ▼ queues events, processes when clock reaches ev.minute
Visual clock (setInterval, 5s/tick)
```

**The bug**: the simulation runs at 2s/tick, the browser polls every 2s. If the browser
tab is briefly backgrounded or a poll fires slightly late, it returns a batch of multiple
minutes at once (e.g. minutes 59, 62, 65, 68 in one response). These are queued
and shown one-per-visual-tick — but the **score in the DB is already at the final batch
value** (6:4), so the scoreboard jumps before the commentary reaches those minutes.

Additional problems:
- Poll latency: 0-2s gap between event creation and display
- Double-timing: simulation pace (2s/tick) and visual clock pace (5s/tick) can drift
- "Future events" in the queue: the browser sees events for minutes it hasn't visually
  reached yet, requiring complex queue management

---

## Proposed Solution: SSE-Only, Event-Driven Clock

Replace the polling mechanism entirely. The browser connects to the **Go SSE hub** and
receives events exactly when they are generated by the simulation.

The clock in the browser becomes **event-driven**: it advances only when an event
(or a `tick` heartbeat) arrives from the server. No independent timer, no queue.

```
SimulateMatchJob (PHP, 2s/tick)
    │
    ├─► writes event to DB (match_event)
    │
    └─► publishes to Redis pub/sub channel: "match:{fixtureId}"
              │
              ▼
        Go SSE Hub (subscribes to Redis)
              │
              └─► SSE push to browser (EventSource)
                        │
                        ▼
                  Browser receives event → updates clock → shows event
```

## Architecture Components

### 1. PHP → Redis pub/sub (new)

After `saveEvent()` in `MatchEngine`, publish the event to Redis:

```php
// In MatchEngine::saveEvent(), after $event->save():
if (Yii::$app->has('redis')) {
    Yii::$app->redis->publish(
        "match:{$fixture->id}",
        json_encode([
            'type'      => 'event',
            'id'        => $event->id,
            'minute'    => $minute,
            'event_type'=> $type,
            'team_side' => $side,
            'detail'    => $event->detail,
        ])
    );
}
```

Also publish a `tick` heartbeat every tick (even when no significant event):
```php
Yii::$app->redis->publish("match:{$fixture->id}", json_encode([
    'type'   => 'tick',
    'minute' => $currentMinute,
    'phase'  => $state->phase,
    'home_score' => $state->home_score,
    'away_score' => $state->away_score,
]));
```

### 2. Go SSE Hub: subscribe to Redis (enhanced)

Currently the Go hub only broadcasts from the Go engine. It needs to also subscribe to
Redis pub/sub and forward messages to connected SSE clients.

```go
// In stream/hub.go — new goroutine started at init:
func (h *Hub) SubscribeRedis(redisAddr string) {
    // Connect to Redis, subscribe to "match:*" pattern
    // For each message received, forward to SSE clients
    // for that fixtureId
}
```

The Go hub already has `Broadcast(fixtureID int, message []byte)`. Redis subscription
just needs to call this.

### 3. Browser: EventSource only, event-driven clock

Remove the polling mechanism (`setInterval(poll, POLL_MS)`) entirely.
Connect via `EventSource` to `http://gateway/stream/{fixtureId}`.

```js
const evtSource = new EventSource('/stream/' + FIXTURE_ID);

evtSource.onmessage = function(e) {
    const msg = JSON.parse(e.data);

    if (msg.type === 'tick') {
        // Update clock immediately — no visual timer needed
        updateClock(msg.minute, msg.phase, msg.home_score, msg.away_score);
    } else if (msg.type === 'event') {
        // Show event immediately — no queuing, no clock sync needed
        processEvent(msg);
    }
};
```

**The visual clock is no longer an independent timer.** It simply shows `msg.minute`
when each `tick` heartbeat arrives. This means:
- Clock and events are perfectly synchronized
- No "future event" queue management
- Score updates ONLY when the corresponding tick heartbeat arrives

### 4. Event delivery guarantees

On page load (e.g., refreshing mid-match), the browser fetches existing events
via REST (`/fixture/get-events`) ONCE to render the backlog, then connects to SSE
for live updates. The existing `$lastEventId` mechanism is kept for the initial REST
call only.

## Migration Plan

| Phase | Work | Risk |
|-------|------|------|
| 1 | PHP `MatchEngine::saveEvent()` publishes to Redis | Low — additive change |
| 2 | Go hub subscribes to Redis pub/sub | Medium — Go code change |
| 3 | Browser: remove polling, add `EventSource` | Medium — JS rewrite |
| 4 | Remove `/fixture/get-events` polling endpoint | Low — keep for backlog |
| 5 | Remove `setInterval(tickLive)` and event queue | High — major JS cleanup |

Phases 1-2 can ship and be tested independently (SSE works alongside polling).
Phase 3 replaces polling only when phases 1-2 are stable.

---

## Fallback

If the SSE connection drops (network issue, Caddy restart), the browser falls back
to polling automatically:

```js
evtSource.onerror = function() {
    evtSource.close();
    // Fall back to polling
    pollTimer = setInterval(poll, POLL_MS);
};
```

## What Changes in `SimulateMatchJob`

For **human matches**:
- Keep `sleep(2)` between ticks (pacing for substitution window)
- Add Redis publish after each `advanceTick()`
- Remove the "visual clock" sleep (clock is now driven by SSE ticks)

For **CPU-CPU matches**:
- No pacing needed
- Publish events to Redis for anyone watching the replay live
- Or skip Redis entirely (nobody is watching in real time)

## Open Questions

1. **Redis pub/sub vs HTTP**: Is Redis pub/sub the right channel, or should PHP
   POST directly to the Go HTTP API? Redis is already in the stack, so pub/sub
   is preferred.

2. **Go hub Redis client**: The Go worker currently uses its own DB connection but
   no Redis client. Need to add `github.com/redis/go-redis/v9` or similar.

3. **Tick heartbeat frequency**: Should every tick send a heartbeat, or only when
   something significant happens? Every tick is safer for clock accuracy.

4. **SSE from Go vs from PHP**: The Go SSE hub already exists. Using it keeps the
   architecture clean (Go = real-time streaming, PHP = business logic).

5. **Pre-match ceremony**: The `pre_match` event (SIP-0042 predecessor) is already
   published to DB. It needs to also flow through Redis → Go hub → SSE.

- [x] SSE fallback to polling on connection error/reconnect window
- [x] Event descriptions can still refresh asynchronously (`event_update` + REST update endpoint)

## Implementation Notes (2026-05-19)

Implemented in `v2/views/fixture/live.php` as **SSE-first**:

- Removed local visual timer progression and minute-gated event queue.
- Incoming SSE `state` messages now directly drive minute/progress/phase.
- Incoming SSE `event` messages are rendered immediately (or buffered only while suspense animation lock is active).
- Added fallback strategy:
  - if `EventSource` fails, enable periodic polling (`/fixture/get-events`);
  - periodic SSE reconnect attempt automatically disables fallback when stream is back.
- 42-bis hardening:
  - visible transport badge (`SSE` / `POLL` / `RETRY`);
  - debug toggle (`DBG ON/OFF`) with localStorage persistence and console tracing.

Pragmatic scope choice:
- Existing Go worker already broadcasts `event`, `state`, `event_update` directly to SSE hub.
- Redis pub/sub bridge proposed in original draft was **not required** for current architecture and therefore not introduced.
