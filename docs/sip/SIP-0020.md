# SIP-0020 — Real-Time Match Engine Architecture

| Field   | Value                     |
|---------|---------------------------|
| Status  | Accepted                  |
| Author  | Gold Manager Dev Team      |
| Created | 2026-05-16                |

## Summary

Define the architecture for a tick-based, real-time match simulation engine with
live spectator mode, tactical interventions, and substitutions. Background
workers must run all scheduled fixtures automatically, regardless of whether a
user is watching.

---

## Architecture

### 1. Two-Speed Engine

| Mode        | Who uses it                  | Description                                   |
|-------------|------------------------------|-----------------------------------------------|
| **Background** | Scheduler (every N minutes) | Runs all `SCHEDULED` fixtures silently at the pre-set match time. Persists full event log. |
| **Live**    | Manager watching their match  | Streams the same tick-by-tick simulation via Server-Sent Events (SSE) or polling. Allows tactical intervention. |

The engine is always the **same algorithm**. The only difference is whether
someone is watching.

---

### 2. Tick System

A match has **90 ticks** (minutes). Each tick the engine:

1. Applies form, freshness and condition modifiers.
2. Applies character trait effects (e.g. *Grintoso* gives a bonus in losing situations).
3. Computes team department totals from the **active formation** (only the 11 starters count).
4. Runs the **action resolution** pipeline (see §3).
5. Persists the resulting `MatchEvent` row.
6. Advances `fixture.current_minute`.

---

### 3. Action Resolution Pipeline (multi-step)

```
[Midfield Duel] → win? →
    [Attack side (L/C/R)] → win? →
        [Shot Quality vs Goalkeeper] → goal?
                                     → post/bar (near-miss event)
                                     → save (GK event)
               → lose (defensive clearance event)
    → lose (no chance created)
```

Each step is a weighted random draw using department totals, individual player
stats, tactic bonuses, and character bonuses.

---

### 4. New Tables

| Table            | Purpose                                          |
|------------------|--------------------------------------------------|
| `match_event`    | One row per action per minute (goal, shot, save, tackle, etc.) |
| `match_state`    | Live state: current minute, active formation, pending substitutions |
| `formation`      | Which 11 players are in which of the 64 zones   |

---

### 5. Console Worker

A Yii2 console command `game/run-fixtures` runs every minute via cron:

```
* * * * * docker compose exec -T php ./yii game/run-fixtures
```

Logic:
1. Find all `SCHEDULED` fixtures where `match_date <= NOW`.
2. For each, run one tick, save events, update `fixture.current_minute`.
3. When `current_minute == 90`, set `status = FINISHED`, update standings.

---

### 6. Live View (Phase 5)

- Frontend polls `/api/fixture/{id}/events?since={minute}` every ~10 seconds.
- Manager can POST to `/api/fixture/{id}/substitution` or `/api/fixture/{id}/tactic` 
  which writes to `match_state.pending_actions`, picked up on the next tick.
- When `current_minute == 45`, the engine pauses for a configurable half-time duration.

---

## Acceptance Criteria

- [ ] `match_event` and `match_state` tables exist.
- [ ] `formation` table exists and is used by the engine.
- [ ] `game/run-fixtures` command advances one tick per call for each active fixture.
- [ ] Fixture result and standings are updated when `current_minute == 90`.
- [ ] Engine uses form, freshness, condition and character trait modifiers.
- [ ] A live-view endpoint exists (Phase 5, SSE or polling).
